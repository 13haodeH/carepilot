# CarePilot MVP2：后续开发入口

MVP1 已作为作品集与技术 Demo 冻结。开始任何新的功能、数据采集、评测、Prompt、模型、政策或产品叙事修改前，先阅读 [MVP1 发布决定](../mvp-v1/04-release-decision.md) 与 [归档地图](../mvp-v1/ARCHIVE-MAP.md)。

## MVP2 的基本规则

1. 不修改 MVP1 的历史真人实验记录、冻结 task fixture、真实 Agent 运行、坏例或发布结论。
2. 新增数据、样本、任务、评测或指标必须使用新版本名、新文档和新的运行标识。
3. 每项工作先写清：业务问题、假设、受影响的用户流程、成功标准、失败边界和验证方法。
4. 技术能力只有在能改善“当前工单如何处置”的产品证据时才加入；不得为技术名词恢复 Multi-Agent、Redis、Reranker 或语音。
5. 高风险权益动作继续保持人工最终确认；不得为了压缩时间取消审核。

## 已登记的候选工作

| 优先级 | 工作项 | 进入条件 | 成功标准 |
| --- | --- | --- | --- |
| P1 | 新建视觉冻结样本，补齐 HRA-P-002 的证据不足边界 | 需要继续技术评测封板 | 新样本可完整观察包装内容；旧坏例与原结论不改写 |
| P2 | 设计真实 Tool 审计下的低风险自动处置覆盖率度量 | 有可审计的受控低风险写 Tool 运行 | 明确合格分母、执行分子、状态变化与失败升级；不以实验页人工选择代替 |
| P2 | 新的真人实验协议 | 有明确新问题，且预先定义连续作答/中断记录 | 新版本任务、分析计划与样本口径；不回填 MVP1 时间结论 |
| P3 | 体验优化或技术扩展 | 能直接解决已记录的业务/安全问题 | 先完成 MVP1 对照基线与最小可验证改动 |

## MVP2 工作记录模板

新增工作在此目录创建独立文档，至少包含：

```text
# 工作标题
## 问题与假设
## 范围和不做什么
## 成功标准与失败边界
## 计划修改的文件/数据
## 验证方法
## 结果、决定与下一步
```
