# CarePilot 可追溯性入口

CarePilot 的可追溯性由三层组成：

```text
Git 提交（改了什么）
        ↕
阶段工作记录（为什么改、如何验证、边界是什么）
        ↕
Prompt / 坏例台账（模型行为、失败、修复与新版本）
```

| 资料 | 回答的问题 |
| --- | --- |
| [变更总台账](./CHANGE-REGISTER.md) | 当前可见 Git 提交、阶段记录与发布版本如何对应 |
| [工作记录索引](../worklog/README.md) | 每个阶段的目标、决策、问题、修改、验证与限制 |
| [Prompt 台账](../ai/PROMPT-REGISTER.md) | 哪个 Prompt 真正运行过，哪些只是草稿或假设 |
| [坏例台账](../ai/BADCASE-REGISTER.md) | 出错原因、修复层、复测版本和保留的失败 |
| [MVP1 发布决定](../mvp-v1/04-release-decision.md) | 哪些证据冻结，哪些声明禁止 |

## 追溯规则

每个新的功能、修复、评测、部署或文档治理变更必须至少有：

1. 一个独立 Git 提交；
2. 一份新增或更新的阶段工作记录，列出问题、决策、受影响文件、验证和边界；
3. 若影响模型行为、Prompt、Tool、政策、样本或指标，更新 AI 台账并新建版本；
4. 若是错误或失败，保留原始运行 / fixture / 数据，登记坏例而不覆盖历史；
5. 若更改 MVP1 的实质功能、数据解释或结论，转入 MVP2，而不是修改冻结版本。

## 历史完整性说明

可访问的 Git 历史从 2026-09-11 的公开实验部署提交开始；而阶段 1–25 的工作记录保存了更早的设计、验证与真实运行事实。因此不能假装每个早期工作记录都有一一对应的独立 Git 提交。本目录将它们明确标成“历史工作记录”，后续改动从本次治理起遵守完整映射。
