# 客服提效公开实验部署说明

- 前端：Netlify 静态站，目录 `apps/experiment-public`
- 后端：Render Python Web Service，目录 `apps/api`
- 数据：现有 Supabase PostgreSQL；浏览器不直连数据库
- 数据边界：公开页只调用三个匿名实验 API，不携带 Supabase secret、数据库连接串、DeepSeek Key 或真实业务数据。

## 本次发布记录（2026-09-11）

- 正式实验入口：`https://carepilot-efficiency-experiment.netlify.app/`
- 后端地址：`https://carepilot-api-eoes.onrender.com`
- Supabase `011_customer_efficiency_study.sql` 已应用；后端健康检查确认使用 `database-url`。
- Render 的 `CORS_ALLOWED_ORIGINS` 已精确设为上述正式入口。`DATABASE_URL` 只存放在 Render 服务端。
- 尚未配置 `EFFICIENCY_PILOT_ACCESS_CODE`；因此当前正式入口可采集 `FORMAL` 数据，任何内部 `PILOT` 试跑请求都会被拒绝，直至项目负责人另行在 Render 添加该口令。

## 1. 首次部署顺序

1. 在 Supabase SQL Editor 执行 `data/011_customer_efficiency_study.sql`。它只新增三张实验表，不改写历史 v0.2、工单、政策或模型记录。
2. 将代码推送到一个**私有** Git 仓库；确认 `.gitignore` 已排除 `apps/api/.env.local`、数据库、虚拟环境与构建产物。
3. 在 Render 从该仓库创建服务，或用根目录 `render.yaml` 创建 Blueprint。服务设置为：
   - Root Directory：`apps/api`
   - Build Command：`pip install -r requirements.txt`
   - Start Command：`uvicorn app.main:app --host 0.0.0.0 --port $PORT`
   - Health Check Path：`/health`
4. Render 服务健康后，得到 `https://<render-service>.onrender.com`。先将这个地址写入 `apps/experiment-public/config.js` 的 `CARE_PILOT_API_BASE_URL`。
5. 用 Netlify 发布 `apps/experiment-public`，得到唯一公开实验链接 `https://<netlify-site>.netlify.app/`。
6. 在 Render 将 `CORS_ALLOWED_ORIGINS` 精确设为上述 Netlify 地址（不带末尾 `/`），保存并重新部署。不要使用 `*`。
7. 从已发布的 Netlify URL 完成一次正式端到端试做；确认 `/health` 的 `storage` 是 `database-url` 而不是 `sqlite-dev-fallback`。

## 2. Render 环境变量

以下变量全部只填在 Render 控制台或其受控 Secret 管理中，绝不填入 Netlify、`config.js`、`NEXT_PUBLIC_*` 或 Git：

| 变量 | 用途 |
| --- | --- |
| `DATABASE_URL` | Supabase Session Pooler 的 SQLAlchemy PostgreSQL 连接串，保留 `postgresql+psycopg://` 前缀与 SSL 配置 |
| `SUPABASE_URL` | 服务端验证 Supabase JWT 所需的项目 URL |
| `SUPABASE_PUBLISHABLE_KEY` | API 现有 Auth 流程使用的公开 key；公开实验页不读取它 |
| `SUPABASE_SECRET_KEY` | 仅服务端 Demo Auth/管理能力使用 |
| `SUPABASE_JWKS_URL` | JWT 验签 JWKS 地址 |
| `DEEPSEEK_API_KEY`、模型相关变量 | 仅在真实 Agent 能力使用；公开实验不会调用模型 |
| `CORS_ALLOWED_ORIGINS` | 唯一 Netlify 公开页 URL |
| `EFFICIENCY_PILOT_ACCESS_CODE` | 内部试跑的随机口令；留空时拒绝任何 `PILOT` 试跑请求 |

即使公开实验目前不调用 DeepSeek，也不要把现有服务端变量转移到前端；保留在 Render 是为了让原有受鉴权 API 能继续独立运行。

## 3. 单一公开入口与内部试跑

- 正式测试者只使用根链接：`https://<netlify-site>.netlify.app/`。全程只有这一条公开链接和一张对应二维码。
- 页面首次打开时在该浏览器生成一个 UUID；服务端只为这个 UUID 分配一次 6 道题。回到同一浏览器会恢复原队列。
- 内部试跑不用第二张二维码。研究者在浏览器地址后临时添加 `?pilot=<EFFICIENCY_PILOT_ACCESS_CODE>`，即可写入 `PILOT` 数据；正式链接不会带此参数。试跑口令不要发给正式测试者，也不要放入文档、二维码或截图。
- 同一匿名编号与同一题目的正式提交受数据库唯一约束保护；清除浏览器数据或换设备会生成新的匿名编号，这是公开匿名研究无法仅靠技术完全识别的限制，应在招募说明中要求每人只做一次。

## 4. 自动分配规则

每位参与者都由服务端即时分配 6 题：

1. 始终 3 道自行查信息、3 道系统已整理信息；首题条件按当前总体完成数和匿名编号交叉平衡。
2. 同一人不领取同一个 case 的两个版本。
3. 每次分配时，按当前 `study_mode` 分开统计各条件题的已正式提交数；优先选择完成较少的题。
4. 若完成数并列，则比较已分配但尚未提交数；仍并列时以匿名编号的稳定哈希打散。
5. 新参与者可无限继续加入；系统不会把计数限制在初始 8 人或 P01–P08。

## 5. 二维码

二维码只编码唯一正式链接，不编码口令、数据库地址或其他参数。发布得到最终 Netlify URL 后，可执行：

```bash
npx --yes qrcode -o carepilot-efficiency-experiment.png "https://<netlify-site>.netlify.app/"
```

生成后用手机扫码确认打开的是正式根链接。内部试跑链接不生成二维码。

## 6. 发布前检查

- `GET https://<render-service>.onrender.com/health` 返回 `storage: database-url`。
- Render 日志中不出现连接串、Supabase secret 或模型 Key。
- Netlify 的已发布文件只包含 `index.html`、`app.js`、`style.css` 和公开 API URL；不包含 `.env`、`DEEPSEEK`、`SUPABASE_SECRET` 或 `DATABASE_URL`。
- 用无痕窗口做一次正式实验，确认第六题后只显示感谢页，刷新后不再重新计入同一题。
- 先用内部口令完成 1–2 份 `PILOT` 试跑，再使用不带参数的正式链接开始 `FORMAL` 数据采集。
