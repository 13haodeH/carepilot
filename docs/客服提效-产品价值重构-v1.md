# CarePilot 客服提效产品价值重构 v1

- 决策日期：2026-09-11
- 状态：**产品价值、指标口径和实验设计已冻结；v1 题库与本地运行器已实现，未采集新实验结果**
- 适用范围：CarePilot 求职作品集、产品 Demo、Ops 页面信息层级、后续客服提效实验

## 1. 为什么现在重构叙事

CarePilot 已经具备真实模型、图片 Evidence、受限 Tool Calling、政策引用、权限门禁和审计的技术证据。这些能力是项目可信的必要条件，但不是用户购买或客服使用产品的首要理由。

如果继续以模型、视觉、检索和高风险链路的评测为主线，项目会被理解为“可靠 Agent / 评测工程”项目，和 Wayly 的可信决策叙事重叠。CarePilot 必须回到原始业务问题：客服在一张复杂售后工单上反复查询订单、物流、政策和凭证，最后才有足够信息作出处理决定。

## 2. 新的一句话定位

> CarePilot 是面向电商售后客服的 AI 决策准备工作台：自动汇总订单、物流、政策和凭证，形成可执行的处置包；低风险事项安全推进，高风险事项由客服在同一界面作出有依据的最终决定。

它不是通用 Agent 平台，也不是只回答问题的客服聊天框。

## 3. 与 Wayly 的明确分工

| 项目 | 核心用户问题 | 主要产物 | 作品集主指标 |
| --- | --- | --- | --- |
| Wayly | “我该选择什么方案？” | 面向消费者的可信推荐/决策建议 | 决策质量、信任与安全边界 |
| CarePilot | “这张工单现在怎么处置？” | 面向客服的决策包、低风险推进和人工审批 | 信息准备效率、处置时长、人工操作与 Proposal 结果 |

CarePilot 同样保留规则、人审和评测，但这些是让“客服提效”能够安全落地的底座，而不是首屏价值主张。

## 4. 两条旗舰流程

### A. 物流异常：低风险自动推进

用户投诉物流长期未更新。系统完成订单归属核验、物流查询、已发布政策检索、工单状态更新和通知；客服不需要重复查询，只在异常或失败时介入。

**价值问题：** 对符合条件的低风险工单，系统能否减少人工查询与手工更新，并安全推进到已处理？

### B. 破损/缺件：高风险决策准备

用户上传商品或包装证据。系统汇总订单、签收时间、物流、政策、视觉 Evidence 与风险判断，形成带依据的换货/补件/补充材料 Proposal；客服在同一界面确认、修改、不采用或接手。

**价值问题：** 对不能自动履约的权益类工单，系统能否让客服更快获得足够信息，并更高质量地完成最终判断？

## 5. 指标树与精确定义

### 5.1 作品集首页的五个业务指标

| 指标 | 定义 | 分母/终点 | 适用场景 | 当前状态 |
| --- | --- | --- | --- | --- |
| 安全自动处置覆盖率 | 已安全自动推进的合格低风险工单数 / 进入处置的合格低风险工单数 | 仅含满足订单、政策、风险条件的低风险工单；以状态和 Tool 审计为准 | 物流等低风险 | 待按真实/模拟运行分别计算 |
| 人工信息操作减少 | Manual 条件中位信息检索操作数，与决策包条件中位“额外核验操作数”的差值及变化率 | 从打开工单到选择处置结果；不把最终提交按钮计入 | 全部实验任务 | v1 待测 |
| 决策前信息完整度 | 已具备的必需决策字段数 / 当前场景必需字段数 | 客服首次看到 Proposal 或进入人工审批时计算 | 全部实验任务 | v1 待测 |
| 处理/决策准备时间 | 低风险：打开/提交至 `RESOLVED`；高风险：打开/提交至 `WAITING_REVIEW` 或客服作出最终审核决定 | 高低风险分开汇总，禁止混成一个“平均结案时间” | 全部实验任务 | v1 待测 |
| Proposal 结果 | 高风险 Proposal 的采纳、修改、不采用、人工接手占比 | 仅实际生成 Proposal 的高风险工单；同时展示样本量 | 高风险 | 当前只存在探索性小样本记录 |

### 5.2 信息完整度的字段口径

每个 case 在冻结前声明其必需字段。客服看到的“决策包”须明确指出缺失项，不能用模型置信度代替事实完整度。

| 字段 | 低风险物流是否必需 | 高风险权益是否必需 |
| --- | --- | --- |
| 用户诉求已结构化 | 是 | 是 |
| 订单归属、商品、订单状态 | 是 | 是 |
| 物流/签收信息 | 是 | 是 |
| 已发布政策引用 | 是 | 是 |
| 图片/凭证状态及缺失说明 | 仅有图或场景要求时 | 是；无有效证据也要明确标为缺失/待补 |
| Proposal、风险和下一步 | 是 | 是 |

“完整”不等于必然自动执行：高风险 case 即使字段齐全，仍必须进入人工审核。

### 5.3 次级质量与安全护栏

以下指标继续记录在 Evaluation/技术附录，不作为首屏主 KPI：

- 高风险自动执行次数必须为 0；高风险 Proposal 必须进入人工审核。
- 非法状态跳转、未授权 Tool 成功调用、重复请求造成重复动作必须为 0。
- Policy citation、Tool trace、模型/Prompt/成本记录是否完整。
- Tool 成功率、检索命中、视觉 Evidence 判断、模型延迟和成本。

它们回答“这套提效机制能否安全使用”，不替代“它是否让客服工作更高效”。

## 7. 产品页面与 Demo 的信息层级

### Ops 首屏：展示“决策包”，而非系统 Trace

客服首先应看到：

1. 这张工单的诉求、时效和风险；
2. 已核验的订单、物流、政策和凭证事实；
3. 仍缺什么信息，以及系统已经自动完成什么；
4. 推荐处置、政策依据和客服现在只需做的动作；
5. 高风险时的确认、修改、不采用、接手入口。

Tool trace、模型、Prompt、token、延迟和成本放入“运行详情”或 Admin，不占用客服主决策区。

### Evaluation 首屏：展示业务价值，再展示技术诊断

Evaluation 的第一屏依次展示：安全自动处置覆盖率、人工信息操作、决策前完整度、低风险处理/高风险决策准备时间、Proposal 结果。检索、视觉、Tool 和成本作为可展开的质量诊断层。

## 8. 停止项与后续优先级

在产生 v1 客服提效证据前，停止扩展下列能力：

- 新的模型架构 A/B/C、多 Agent 编排或 Reranker/向量库实验；
- 新增风险角色、权限体系、审计页面或部署范围；
- 为提高单项模型分数而修改已冻结旧评测语义。

允许的技术改动仅限于：实现 v1 所需的业务指标采集、决策包展示、匿名实验运行与结果导出；以及修复会使现有安全/业务路径失真的缺陷。

## 9. P0 完成标准

1. 已冻结 v1 客服提效实验协议、任务集、字段和分析规则。
2. 每个 v1 case 都明确 Manual 条件的分散信息与决策包条件的相同来源事实。
3. 高风险 case 的实验终点是人工可决策或审核完成，不是通过取消审核来缩短时间。
4. 结果页能够分开呈现业务 KPI、质量诊断和安全护栏。
5. 新实验采集前，首页、Demo 讲稿和简历不使用任何“提效提升”结论。
